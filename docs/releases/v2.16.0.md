ProxBalance now updates only to tested releases, and updates back up your data and roll themselves back if the new version doesn't come up healthy. This release also explains the health score, caps how many guests can move into one node per run, respects Proxmox VE 9 HA rules, and adds a Prometheus endpoint.

## Release-only updates

- **Installs update to published releases, not to every commit.** A release is only published after the new GitHub Actions pipeline has run the tests and built the web interface. The update window (click the version number in the top bar) shows the release notes and lets you choose a channel:
  - **Stable** (default): tested releases only.
  - **Beta**: releases plus pre-releases (`vX.Y.Z-rc.N`), for trying a fix before it ships.
  - **Development**: every commit on the checked-out branch, for development and test installs.
- **Updates are safer.** The update now runs in its own systemd unit (`proxbalance-update`), so it survives the restart of the app it is updating. It:
  1. backs up the database (compressed), settings and current web files to `backups/updates/` (the newest 3 are kept);
  2. installs the release's pre-built web interface after checking it against the release's `SHA256SUMS`, so the container no longer needs Node.js to update (it builds locally if the download fails);
  3. restarts ProxBalance and waits for it to report healthy;
  4. goes back to the previous version automatically if it doesn't.

  Each step shows live in the update window.
- **Fresh installs** check out the latest release and use the stable channel. Installing with `PROXBALANCE_BRANCH=<branch>` installs that branch on the development channel.
- **`update.sh`** on the Proxmox host uses the same updater, shows the release notes and asks before updating (`-y` skips the question).
- **The "update available" notification is sent once per new version.** It was sent again on every dashboard load.

## Removed: the branch manager

The branch switcher in the top bar is gone. Its jobs are covered by the update channels: to try a fix, use the beta channel; to develop on a branch, check it out once and use the development channel. These API endpoints now return 404: `/api/system/branches`, `/api/system/switch-branch`, `/api/system/branch-preview/<branch>`, `/api/system/rollback-branch`, `/api/system/clear-testing-mode`. `previous_branch` is no longer in `/api/system/info`.

## Balancing

- **The health score explains itself.** Each node card in Cluster Health and the node side panel has a "Why N?" breakdown listing each penalty with the reading behind it, e.g. "CPU peak this week 82% (over 80%) +10", and how base load and penalties add up to the headroom figure. The health tile also shows the cluster's memory and CPU spread (most loaded minus least loaded node).
- **Cap on moves into one node per run.** New setting "Max into one node per run" (Automation → What to Migrate → Limits, 0 = no limit, default off). It stops one quiet node being flooded in a single run. Manual batch plans show a warning with a one-click "leave out the extra moves".
- **Proxmox VE 9 HA rules are respected.** ProxBalance reads `/cluster/ha/rules` and won't move a guest onto a node running a negative-affinity peer, or onto a node a strict node-affinity rule excludes. It warns when positive-affinity peers would move with the guest. Recommendations, automation, evacuations and manual moves all check this, and the server refuses a blocked move with 409. Proxmox VE 8 HA groups (restricted) are honoured the same way. No effect on clusters without HA rules.
- **"Seen in N runs" on suggestions.** Each suggestion shows how many consecutive automation runs have suggested it and how many are needed before automation acts (e.g. "seen 2 of 3 runs"), with an explanation on tap.
- **Stricter consistency count.** A run with no suggestions now restarts every guest's count, as a run that didn't mention the guest already did. Automation therefore waits longer before moving a guest that keeps dropping in and out of the suggestions.

## Monitoring

- **Prometheus endpoint at `/api/metrics`.** Node CPU (current and 15-minute), memory, IO wait, score, running guests and unmovable CPU; per-guest CPU, memory and placement; collection age; automation state, last run and migration counts. A ready-made Grafana dashboard is in `docs/grafana/`, and setup is in `docs/PROMETHEUS.md`. It follows the same `api_key` rule as the rest of the API.

## Reliability

- **Proxmox API calls have explicit timeouts** (5 s connect; 8 s for normal reads, 30 s for slow reads and migrations).
- **A migration request is never sent twice.** If Proxmox's answer is lost, ProxBalance looks up the task it started instead of resubmitting; if it can't tell, it reports the outcome as unknown (HTTP 504) rather than retrying.
- **Bare `NaN`/`Infinity` values from Proxmox** no longer break API responses.
- **Collector errors are labelled by kind** (network, timeout, auth, application) in the log and in `cluster_cache.json` (`collection_errors`).
- **"Run now" blocks while a migration is in flight.** The check called a function that no longer existed, and the error was silently ignored.

## Upgrading

- **Installs following `main` (most installs):** the in-app updater pulls this version like any other commit. After that, the update window offers "switch to release v2.16.0"; accepting moves the install onto the stable channel, and from then on it only updates to releases.
- **This first update is still done by the old updater.** If the web interface doesn't change afterwards, run once in the container: `bash /opt/proxmox-balance-manager/post_update.sh && systemctl restart proxmox-balance`. See "An in-app update failed or didn't update the UI" in `docs/TROUBLESHOOTING.md`.
- **Scripts that called the branch-manager endpoints** need updating (they now return 404).
- See `docs/RELEASING.md` for channels, how updates run and roll back, and how releases are cut.
