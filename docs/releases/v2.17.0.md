This release answers three new questions — could the cluster survive losing a node, are guests sized for what they use, and will a move fit on the target's disks — makes the dashboard work properly on phones, and blocks cross-site requests.

## What if a node fails?

A new card on the Insights page lets you pick a node and see what would happen to its running guests, using the latest collected data:

- Where each guest would restart (largest first, onto the node with the most free memory, up to 95% memory, respecting anti-affinity tags and Proxmox HA rules), each survivor's memory before and after, and anything that wouldn't fit.
- A chip per node: **can fail**, **N can't restart** (passthrough hardware or node-local bind mounts) or **N left out** (doesn't fit).
- By default it answers the capacity question — could the other nodes hold this node's guests, for example for planned maintenance? A plain line underneath says when guests on node-local disks wouldn't restart on their own after an unplanned failure. The **Unplanned failure** toggle shows that view in full.

The node side panel gets one line, "If this node fails: …", linking to the card. API: `GET /api/simulate/node-failure`.

## Right-sizing hints

A **Right-sizing** card on Insights lists guests whose allocation doesn't match their last 7 days of use: idle CPU (suggesting fewer vCPUs that still cover the guest's 95th-percentile load), oversized memory (with 30% headroom over peak use) and guests that are mostly stopped. At least 3 days of history are required.

Totals count **VMs only** ("VMs could free 1 vCPU across 2 VMs"); container hints are in a collapsed group, because container limits aren't reserved on the host. The guest side panel shows the guest's own hint. API: `GET /api/insights/rightsizing`.

## Target storage after a move

Suggestions, the Move-to panel and the migrate dialog now show the target node's storage use after the move for every disk copied onto node-local storage, e.g. "local-lvm on pve6: 72% → 88%", counting other moves into the same node. Shared storage is never flagged.

- A move whose disks wouldn't fit is skipped by automation (`target_storage_full`), disabled in the UI and shown as **Blocked: storage full**.
- Above 90% the move still runs, shown as **Storage nearly full**.

The collector now records each guest's disks with their storage and size, whether each storage is shared, and passed-through devices. The new fields appear after the first collection on this version.

## Dashboard on phones

- The Cluster and Automation tab rows stay on one line and scroll sideways instead of wrapping.
- The node table and the automation switches fit on narrow phones (360 px).
- Buttons, chips and links are at least 40 px tall on phones.
- The cluster health tile says what is going on instead of "Good / Tight / Under pressure": **All nodes have room**, or the busiest node and its biggest problem, e.g. **pve4: disk wait high this week**, with its headroom underneath.

## Security

- **Cross-site requests are blocked.** State-changing API requests (POST, PUT, PATCH, DELETE) that a browser marks as coming from another site get 403. The app's own pages, scripts, services and the MCP server are unaffected, and a valid API key skips the check. Set `csrf_protection: false` to turn it off for unusual reverse-proxy setups. See "403 Cross-site request blocked" in `docs/TROUBLESHOOTING.md`. Closes #109.

## Upgrading

Update from the update window (click the version number in the top bar). The updater backs up the database, settings and web files, installs the tested web bundle, restarts ProxBalance and rolls back automatically if it doesn't come back healthy. The node-failure card and storage projections fill in after the next collection.
